# 실전 소개 스크립트 — 팀 소개용

> 동료들에게 말로 소개할 때 쓰는 문서.
> 더 깊은 질문이 나올 때만 [`팀-소개-총정리.md`](./팀-소개-총정리.md)를 찾아보면 됨.

이 프로젝트를 한 문단으로:

> "구현-검증 루프 설계 및 브라우저 검증 도구 제작: AI의 결과물을 사람이 매번 확인 후 재구현을 시키는 과정이 빠른 개발에 병목 요인이라고 판단했습니다. AI가 실제 브라우저 환경에서 스타일과 인터랙션을 검증하고, 실패하면 수정까지 이어갈 수 있도록 구현-검증-재구현 루프를 설계했습니다."

소개는 이 문단 안에 있는 4가지 흐름이면 충분하다:
**① 무슨 병목이었나 ② 루프가 뭔가 ③ 검증을 어떻게 하나 ④ 그래서 뭐가 좋아졌나**

---

## 1. 딱 외울 세 문장

이것만 자연스럽게 나오면 나머지는 다 따라온다:

1. **"AI가 코드를 고쳐줘도, 브라우저 가서 잘 됐는지 확인하는 건 매번 사람이 해야 했어요. 그게 병목이었습니다."**
2. **"그래서 AI가 직접 브라우저를 열어보고 '색이 맞나, 클릭이 되나, 에러가 없나'를 확인하고, 틀렸으면 스스로 고치게 만들었어요."**
3. **"핵심은 AI한테 판정을 맡기지 않은 거예요. AI는 '뭘 확인할지'만 정하고, 실제 확인과 합격 판정은 미리 만들어둔 코드가 해요. 그래야 결과가 안 흔들리니까요."**

---

## 2. 왜 만들었나 — 스토리로 말하기

AI 코딩 도구(Claude Code)로 개발하면 이런 일이 반복된다:

```
나: "버튼 색 바꿔줘"
AI: (코드 수정) "완료했습니다!"
나: (브라우저 열고, 새로고침하고, 그 페이지 찾아가서, 눈으로 확인)
나: "아니야, 색이 다르게 나왔어"
AI: (다시 수정) "완료했습니다!"
나: (또 브라우저 가서 확인...)
```

**AI는 빠른데, 확인하는 내가 느려서 전체 속도가 안 나온다.**
AI는 자기가 고친 결과를 브라우저에서 볼 수 없으니 "완료했습니다"가 진짜인지 아무도 모른다.

그래서 만든 것: **AI에게 브라우저를 보는 눈을 달아주는 도구.**

## 3. 구현-검증-재구현 루프가 뭔가

말 그대로 이 그림이 전부다:

```
        구현                검증                 재구현
   AI가 코드 수정  →  AI가 브라우저에서   →  틀렸으면 AI가
                      직접 확인             스스로 고치고 다시 확인
                          │
                       맞으면 ✅ 끝
```

이전에는 "검증" 자리에 **사람**이 있었고, 지금은 **AI + 이 도구**가 있다.
사람은 마지막 결과만 보면 된다.

## 4. 검증을 어떻게 하나 — 한 단계만 깊게

여기서 이 도구의 유일한 "설계 포인트"가 나온다. 비유는 **자동 채점기(OMR)**.

- AI한테 "화면 보고 잘 됐는지 판단해줘"라고 하면 → 같은 화면인데도 어제는 "잘 됐다", 오늘은 "이상하다"고 답할 수 있다. AI의 판단은 흔들리니까.
- 그래서 반대로 했다: **AI는 "몇 번 칸을 볼지"만 정한다.** "이 버튼의 배경색이 파란색이어야 해" 까지만. 그 다음 실제로 색을 읽고 비교해서 ✅/❌를 매기는 건 **미리 만들어둔 코드**가 한다.

```
AI 역할:   "이 카드의 배경색이 rgb(214, 234, 250)이어야 해"  ← 뭘 볼지만 지정
도구 역할:  실제 화면에서 그 값을 읽음 → 비교 → ✅ PASS / ❌ FAIL  ← 기계적 판정
```

이러면 **같은 검증은 100번 돌려도 같은 결과**가 나온다. 이게 "검증"이라는 말을 쓸 수 있는 이유.

기술적으로 어떻게 브라우저를 보냐고 물으면 이 한 줄이면 충분:

> "개발할 때 쓰는 크롬을 디버깅 모드로 띄워두면, 도구가 거기 연결돼서 화면의 실제 값(색, 크기, 에러 로그)을 읽어옵니다. Playwright라는 브라우저 자동화 라이브러리를 사용했어요."

## 5. "실패하면 수정까지 이어진다"는 건 어떻게?

검증이 ❌ FAIL로 나오면 결과에 **"뭐가 어떻게 달랐는지"** 가 구조적으로 담겨 있다:

```
❌ FAIL — 배경색: 기대값 rgb(214, 234, 250) / 실제값 rgb(255, 255, 255)
```

AI는 이걸 보고 원인을 찾아 코드를 고치고, **다시 검증을 돌린다.** 통과할 때까지 (무한루프 방지를 위해 최대 2회, 그래도 안 되면 사람에게 보고).

한 발 더 가면: 코드를 수정할 때마다 **자동으로** 이 검증이 돌게 하는 옵션도 있다. 켜두면 "수정 → 검증 → 보고"가 사람 개입 없이 돈다.

## 6. 기존 방법과 뭐가 다른가 — 비교는 두 축

비교 질문은 반드시 이 둘 중 하나로 온다. **어느 축의 질문인지 먼저 분간**하고 답하면 된다.

### 축 1 — "기존 테스트랑 뭐가 달라요?" → E2E 테스트와 비교

실제 브라우저를 띄워 동작을 확인한다는 점에서 하는 일이 가장 비슷한 게 E2E 테스트(Playwright Test, Cypress). 차이는 **시점과 방식**:

| | E2E 테스트 | 이 도구 |
|---|---|---|
| 언제 | 완성 후, CI에서 | **개발 중**, 수정 직후 |
| 검증 항목 | 사람이 미리 코드로 작성 | AI가 방금 고친 것에 맞춰 즉석 도출 |
| 환경 | 매번 깨끗한 컨텍스트에서 처음부터 | **지금 보던 브라우저 상태 그대로** |

> 답변: "E2E와 하는 일은 비슷한데 시점이 달라요. E2E는 완성 후 안전망이고, 이건 개발 중 간 보기예요. 대체가 아니라 테스트 짜기 전 단계의 공백을 메우는 거죠."

(참고: 유닛 테스트는 브라우저가 없고, Percy 같은 시각 회귀는 픽셀 비교라 애초에 하는 일이 달라서 비교 대상이 아님.)

### 축 2 — "Playwright MCP 같은 AI 도구랑 뭐가 달라요?" → 판정 주체 비교

이 도구의 정체성 자체는 "AI에게 브라우저를 쓰게 해주는 도구" 계열. 같은 계열 안에서의 차이는 **누가 합격/불합격을 판정하느냐**:

| | AI 브라우저 도구 (Playwright MCP 등) | 이 도구 |
|---|---|---|
| 판정 주체 | AI가 화면을 읽고 판단 | **코드가 기계 비교** |
| 같은 검증 2번 | 결과가 흔들릴 수 있음 | 항상 같음 |
| 비용 | 화면 전체를 읽어 무거움 | 필요한 값만 읽어 가벼움 |

> 답변: "걔네는 AI가 화면을 보고 판단해서 결과가 흔들릴 수 있는데, 이건 AI는 '뭘 볼지'만 정하고 판정은 코드가 해서 매번 같은 결과가 나와요."

### 포지션 한 문장 (외워두기)

> **"AI 브라우저 도구의 유연함과 E2E 테스트의 결정성 사이의 빈 자리 — 둘 다와 비교되지만 둘 다 아닌 지점."**

## 7. 팀원 소개용 3분 대본

팀에 소개할 땐 기술 설명보다 **써보고 싶게** 만드는 게 목표:

> "다들 Claude로 코드 고치고 나서 브라우저 가서 확인하는 거 귀찮지 않아요?
>
> 이거 설치하면 Claude한테 '잘 됐는지 확인해줘' 한마디만 하면 돼요. Claude가 직접 브라우저를 열어보고 — 색이 맞는지, 버튼이 눌리는지, 콘솔 에러가 없는지 — 확인하고 이렇게 보고해요:
>
> ✅ PASS — 카드 배경색 적용 확인 / 콘솔 에러 0
>
> 틀렸으면 지가 알아서 고치고 다시 확인해요. 특히 좋은 건 **Figma 시안대로 됐는지 검증** — 폰트 크기, 색, 여백을 시안 값이랑 정확히 비교해줘요. 눈대중이 아니라 픽셀 값으로요.
>
> 설치는 Claude Code에서 두 줄이면 끝나요. (`/plugin marketplace add ...`)"

질문 들어오면 그때 4번(자동 채점기 비유)으로 답하면 된다.

## 8. 예상 질문 & 짧은 답

소개하고 나면 나올 법한 질문들. 답은 전부 3~4문장 안으로.

**Q. "구현-검증 루프"가 뭔지 설명해주세요.**
> AI가 코드를 수정하면(구현), AI가 실제 브라우저에서 결과를 확인하고(검증), 틀렸으면 스스로 고쳐서 다시 확인하는(재구현) 사이클입니다. 원래 검증 단계를 매번 사람이 했는데, 그걸 자동화해서 사람은 최종 결과만 보게 만든 거예요.

**Q. 왜 그게 병목이라고 판단했나요?**
> AI가 코드 고치는 건 수십 초인데, 제가 브라우저 열고 확인하고 피드백 주는 건 몇 분씩 걸렸어요. 그리고 AI는 자기 결과물을 못 보니까 "완료했습니다"가 실제로 완료인지 보장이 없었고요. 전체 개발 속도가 AI가 아니라 제 확인 속도에 묶여 있다는 걸 느꼈습니다.

**Q. 검증은 기술적으로 어떻게 하나요?**
> MCP 서버로 만들었어요. 개발용 크롬을 디버깅 모드로 띄워두면 Playwright로 거기 연결해서, AI가 지정한 요소의 실제 값 — 색상, 크기, 콘솔 에러 — 을 읽어와서 기대값과 비교합니다. 중요한 건 비교와 합격 판정을 AI가 아니라 코드가 한다는 점이에요. AI 판단은 흔들릴 수 있어서, AI는 "뭘 확인할지"만 정하게 했습니다.

**Q. 실패하면 수정으로 이어진다는 건?**
> 검증 결과에 "기대값 vs 실제값"이 구조적으로 담겨 나와요. AI가 그걸 보고 코드를 고치고 재검증합니다. 무한루프 방지로 2회까지 시도하고, 그래도 안 되면 시도 내역과 함께 사람에게 넘기게 했어요.

**Q. 효과가 있었나요?**
> 확인하러 브라우저를 왔다 갔다 하는 시간이 거의 없어졌고, 특히 Figma 시안 값(폰트·색·여백)을 눈대중이 아니라 픽셀 값으로 대조하니까 미묘한 스타일 누락을 훨씬 잘 잡아요. 그리고 검증 결과가 "뭘 확인했는지" 기록으로 남아서, AI의 "완료했습니다"를 신뢰할 수 있게 됐습니다.

**Q. 기존 테스트 도구와 뭐가 다른가요?**
> (→ 6번의 답 그대로)

**Q. 만들면서 어려웠던 점은?**
> 타이밍이요. React 앱은 화면이 뜬 것처럼 보여도 아직 로딩 중이라, 너무 빨리 검사하면 멀쩡한 코드가 실패로 나와요. 그래서 "로딩이 끝날 때까지 기다렸다가 검사"하는 로직을 도구 안에 넣어서, AI가 타이밍을 신경 쓸 필요가 없게 했습니다. 색상 표기 문제도 있었어요 — 같은 색인데 코드는 hex, 브라우저는 rgb로 표현해서, 비교 전에 표기를 통일하는 처리를 넣었고요.

**Q. AI 도구로 개발했다면서요, 직접 한 역할은 뭔가요?**
> 구현 자체는 AI와 함께 했고, 제 역할은 문제 정의와 설계 결정이었어요. "확인 병목"이라는 문제를 정의한 것, "판정을 AI에게 맡기면 안 되고 코드가 해야 한다"는 방향을 정한 것, 검증 전용으로 역할을 좁힌 것, 그리고 매 단계 결과물을 실제 제 개발 루프에서 써보면서 안 되는 부분을 찾아 다시 시킨 것이요. AI를 쓰더라도 뭘 만들지·왜 그렇게 만들지는 사람이 정해야 하더라고요.

**Q. 한계는 없나요?**
> 크롬 계열 브라우저에서만 동작하고, 픽셀 단위의 미세한 시각 차이는 못 잡아요. 그건 의도한 범위이기도 한데 — 이 도구는 개발 중 빠른 확인용이고, 정밀 시각 회귀나 크로스브라우저 테스트는 기존 전문 도구의 영역으로 남겨뒀습니다.

**Q. 구현하는 AI와 검증하는 AI가 분리되어 있나요? (객관성)**
> 큰 변경일 때는 별도 에이전트에게 검증을 위임해서 컨텍스트가 분리되지만, 작은 변경은 같은 에이전트가 검증까지 합니다. 대신 객관성은 분리가 아니라 다른 데서 나와요 — **합격/불합격 판정 자체를 AI가 못 내리게** 했거든요. 판정은 도구 코드가 기대값과 실제값을 기계적으로 비교해서 내리고, 뭘 검사했는지도 기록으로 남아요. 자기가 짠 코드라고 후하게 채점할 방법이 없는 구조입니다.

**Q. 크롬 "디버깅 모드"가 뭐고, 왜 그걸 써야 하나요?**
> 크롬을 특정 옵션(`--remote-debugging-port`)으로 띄우면 외부 프로그램이 그 크롬을 들여다보고 조종할 수 있는 통신 채널이 열려요. 평소 크롬은 이 문이 닫혀 있어서, 어떤 도구도 화면을 읽을 수 없습니다. 그래서 이 채널이 필요했는데 — 한 가지 문제가 있었어요. 원래 쓰던 크롬을 그대로 쓰고 싶었지만, 개인 크롬에 이 문을 열면 로컬의 아무 프로그램이나 제 로그인 세션·쿠키를 읽을 수 있는 보안 위험이 생겨요 (실제로 최신 크롬은 개인 프로필엔 이 옵션을 막아놨습니다). 그래서 **개인 크롬과 완전히 분리된 개발 전용 프로필(폴더)을 따로 만들어** 그것만 디버깅 모드로 띄우게 했어요. 개발할 땐 그 크롬(9223 포트)에서 작업하고, 도구도 같은 포트에 연결됩니다. "쓰던 화면 그대로 검증"은 유지하면서 개인정보 노출은 없앤 거죠.

**Q. 왜 Playwright를 썼나요? 크롬 채널(CDP)을 직접 쓰면 안 되나요?**
> 처음엔 실제로 raw CDP로 직접 만들었다가 갈아탔어요 — 이론이 아니라 겪어보고 바꾼 겁니다 (전환 과정이 리팩터 기록으로 남아 있어요). raw CDP의 문제는 두 가지였어요. 첫째, 요소를 "그 순간의 참조"로만 잡을 수 있어서 React가 화면을 다시 그리면 참조가 죽어요 — 클릭 직전에 버튼이 사라지는 불안정함(flaky)이 계속 생겼습니다. 둘째, "요소가 보이고, 안 가려졌고, 클릭 가능해질 때까지 기다리기"를 전부 손으로 짜야 해요. Playwright는 이걸 이미 해결해둔 도구예요 — 요소를 참조가 아니라 **조건**으로 기억해서 쓸 때마다 다시 찾아주고(Locator), 대기·재시도가 내장돼 있어요. 결정적 검증에 필요한 안정성 기반을 공짜로 얻은 거죠. 그러면서도 이미 떠 있는 크롬에 붙는 기능(connectOverCDP)은 그대로 지원하고요.

**꼬리 질문 대비 — "E2E 테스트(Playwright Test)와 비교한다면서 Playwright를 쓰는 건 모순 아닌가요?"**
> 모순이 아니에요. Playwright는 한 이름 아래 3개 층이 있거든요:
>
> ```
> ③ @playwright/test  — 테스트 러너 (격리 컨텍스트, 병렬 실행)  ← 비교 대상. 안 씀
> ② playwright        — 라이브러리 + 전용 브라우저 3종 번들     ← 안 씀
> ① playwright-core   — 브라우저 조종 라이브러리만              ← 이것만 씀
> ```
>
> 제가 비교하는 건 ③테스트 **러너**이고, 쓰는 건 ①조종 **라이브러리**예요. "Playwright Test는 안 쓰고, Playwright 라이브러리로 검증 레이어를 직접 만들었다"가 정확한 문장입니다.
>
> ②가 아니라 ①을 쓴 이유도 이어져요 — ②는 설치할 때 전용 브라우저를 수백 MB 다운로드하는데, 이 도구는 브라우저를 직접 띄우지 않고 **이미 떠 있는 진짜 크롬에 붙기만** 하니까(connectOverCDP) 브라우저가 딸려올 필요가 없어요. 비유하면, 새 차를 뽑는 게 아니라 시동 걸려 있는 내 차 운전석에 앉는 거라 운전 기술(라이브러리)만 있으면 되는 겁니다.

**Q. 조작은 agent-browser에 맡겼다면서, 검증엔 왜 그걸 못 쓰나요?**
> agent-browser의 출력물은 접근성 트리나 스크린샷 — **AI가 눈으로 읽으라고 만든 것**이에요. 검증에 필요한 건 다릅니다 — 특정 요소의 실제 색상·크기 값을 프로그램으로 정밀하게 읽고, 검사 여러 개를 묶어 한 번에 질의하고, 기계적으로 비교하는 로직인데, 이건 CLI가 아니라 라이브러리 수준의 브라우저 접근이 있어야 만들 수 있어요. 그래서 조작(유연함이 중요)은 agent-browser, 검증(정밀함·일관성이 중요)은 Playwright로 직접 구축 — 같은 크롬을 공유하면서 역할만 나눴습니다.

**Q. AI한테 테스트 코드를 짜게 하면 되지 않나요?**
> 두 가지 이유로 개발 중 확인엔 안 맞았어요.
>
> 첫째, **테스트 코드는 매번 깨끗한 컨텍스트에서 처음부터 실행돼야 해요.** 격리가 테스트의 기본 철학이니까요. 그래서 로그인하고 그 화면까지 도달하는 걸 매번 재현해야 해서 느리고 — 더 결정적으로는, "지금 열어둔 모달, 입력하다 만 폼" 같은 **지금 상태를 아예 볼 수 없어요.** 저는 이미 그 화면을 띄워놓고 있는데, 테스트는 백지에서 다시 시작하거든요.
>
> 둘째, **구현 중이라 계속 바뀌는 코드에 테스트를 붙이면 두 가지 낭비가 생겨요.** 코드가 바뀔 때마다 테스트도 따라 고쳐야 하고(확인을 도우려고 만든 게 일거리가 됨), "방금 이 색 바뀌었나?" 같은 **한 번만 확인하면 되는 일까지 영구 보관되는 테스트 코드로 쌓여요.** 남길 가치를 아직 모르는 시점에 자산화가 강제되는 거죠.
>
> 그래서 순서를 뒤집었어요. 기본은 일회성 확인으로 가볍게 처리하고, **같은 확인을 여러 번 반복하고 있다는 게 보이면 — 그게 회귀 테스트로 남겨야 한다는 신호예요 —** 그때 JSON으로 굳혀서 반복 재생합니다. 테스트 코드는 짜기 전에 "뭘 남길지" 미리 정해야 하지만, 이 방식은 실제로 반복된 것만 남기니까 남길 대상을 고르는 데 틀릴 수가 없어요.

**꼬리 질문 대비 — "테스트도 로그인 저장 기능(storageState) 있지 않나요?"**
> 맞아요, 로그인 상태를 파일로 저장해뒀다 복원하는 기능이 있어서 로그인 문제는 완화돼요. 하지만 그것도 "저장해둔 세션을 백지에서 복원"하는 것이지, **지금 내가 보던 화면 — 세 번 클릭해서 열어둔 모달, 입력하다 만 폼 — 에 붙는 건 어떤 설정으로도 불가능**해요. 격리 철학 자체가 "매번 처음부터 재현"이니까요. 개발 중 확인에서 원하는 건 재현이 아니라 "지금 이 상태 그대로 보기"였고, 그래서 attach(붙기) 방식을 선택했습니다.
