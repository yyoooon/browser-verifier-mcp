# 브라우저 검증 플러그인, 진짜 쉽게 이해하기

> browser-verifier와 Playwright MCP를 **초등학생도 알 수 있게** 풀어쓴 문서.
> "채점" 비유 하나로 처음부터 끝까지 갑니다.

---

## 0. 큰 그림

너는 웹사이트를 만드는 사람이에요. 코드를 고치면 **브라우저에서 진짜 잘 됐는지** 봐야 해요.

Claude(AI)는 너를 도와주는 친구인데, **네 화면을 못 봐요.** 눈이 없어요.

그래서 Claude한테 **"눈"을 달아주는 도구**가 두 개 있어요. 둘의 진짜 차이는 **"잘 됐는지 합격/불합격을 누가 정하느냐"**예요.

| 도구                 | 한마디로                   | 비유                      |
| -------------------- | -------------------------- | ------------------------- |
| **browser-verifier** | 정해둔 답과 기계적으로 대조 | **자동 채점기(OMR 기계)** |
| **Playwright MCP**   | 화면 읽고 AI가 직접 판단    | **눈으로 채점하는 조교**  |

---

## 1. 둘이 뭐가 다른데? — "합격/불합격을 누가 정하나"

검증은 결국 "이거 잘 됐나?"에 **✅/❌를 매기는 일**이에요. 그 채점을 **누가** 하느냐가 핵심 차이.

**browser-verifier = 자동 채점기(OMR 기계)**
👉 정답(기대값)을 미리 정해두면, 기계가 답안과 **1:1로 기계적으로 대조**해서 ✅/❌.
사람 판단이 안 들어가서 **매번 똑같은 결과**가 나와요.
👉 게다가 OMR은 **정해진 칸만** 읽어요. 답안지 전체를 안 보고 필요한 칸만 콕 → **빠르고 가벼움**.

**Playwright MCP = 눈으로 채점하는 조교**
👉 화면(답안)을 **통째로 읽고**, AI가 "음, 맞는 것 같다" 하고 직접 판단해요.
유연하지만 사람(AI) 판단이라 **같은 걸 봐도 결과가 흔들릴 수** 있어요.
👉 어디에 뭐가 적혔는지 모르니 **답안지를 처음부터 끝까지** 다 읽어야 해요 → **느리고 무거움(토큰 많이 씀)**.

### 그래서 차이가 두 가지로 나옴

| | **자동 채점기** (browser-verifier) | **눈 채점 조교** (Playwright MCP) |
| --- | --- | --- |
| **누가 판정?** | 코드가 기계적으로 → 항상 같은 결과 | AI가 눈으로 → 흔들릴 수 있음 |
| **얼마나 읽나?** | 필요한 칸만 콕 → 빠름·저토큰 | 화면(접근성 트리) 통째로 → 느림·고토큰 |

사실 이 둘은 한 뿌리예요. **코드가 판정하려면** "무엇을 볼지"부터 정해야 하니 → 그것만 콕 읽고, **AI가 판정하려면** 일단 화면을 다 봐야 하니 → 통째로 읽어요. **누가 채점하냐가 얼마나 읽냐까지 결정**해요.

> 참고: browser-verifier는 **네가 보던 화면 그대로**에 붙어서 확인해요(아래 2~6장). Playwright MCP는 기본은 새 브라우저지만 옵션으로 붙일 수도 있어요. 근데 둘의 **진짜** 차이는 "어디서 보냐"보다 위의 **"누가 채점하냐 + 얼마나 읽냐"**예요.

---

## 2. "명령할 때마다 브라우저를 새로 띄워?"

❌ 아니요!

Playwright MCP는 **한 번 띄우면 계속 그 브라우저를 써요.**
명령 1개마다 새로 띄우는 거 아니에요. 한 창으로 쭉 다녀요. 상태(로그인, 탭)도 그대로 쌓여요.

---

## 3. "Claude 끄면 브라우저도 꺼져?"

브라우저 수명은 **"대화"가 아니라 "MCP 서버 프로세스"**에 묶여 있어요.

| 동작                      | 브라우저            |
| ------------------------- | ------------------- |
| 대화만 지움(`/clear`)     | ✅ 안 꺼짐          |
| 새 대화 시작              | ✅ 안 꺼짐 (공유됨) |
| **Claude 앱을 완전히 끔** | ❌ 같이 꺼짐        |

- browser-verifier가 붙는 브라우저는 **네가 직접 띄운 거라서** 안 꺼져요.
- Playwright MCP가 띄운 브라우저는 앱 끄면 같이 닫혀요.
- 예외: Playwright MCP를 **CDP 연결 모드**로 쓰면 외부 브라우저에 붙기만 해서 안 꺼져요.

---

## 4. "여러 탭도 볼 수 있어?"

✅ 네! Playwright MCP는 탭 여러 개 열고, 옮겨다니고, 닫고 다 돼요.

단, **"이 탭 볼래" 하고 옮긴 다음에** 만져야 해요. 안 옮기면 옛날 탭을 만져요.

```
1. 탭 옮기기 (select)   ← 먼저
2. 클릭 / 확인          ← 그 다음
```

browser-verifier는 탭 목록만 봐요. 탭 생성·전환은 Playwright MCP 쪽이 본격적이에요.

---

## 5. "개발하면서 바로 확인할 땐 새 브라우저가 왜 불편해?"

Playwright MCP는 기본적으로 **빈 새 브라우저**에서 시작하기 때문이에요. (옵션 주면 네 화면에 붙일 수도 있지만 기본은 새 창)

예를 들면:

> 네 화면엔 이미 **로그인 → 모달까지 띄워놓음**.
> 근데 새 브라우저는 빈 상태라서, **그걸 다시 처음부터 만들어야** 확인 가능. 😩

| 단점                 | 왜 불편                                  |
| -------------------- | ---------------------------------------- |
| 상태 재구성          | 로그인·라우팅·데이터를 매번 다시 만듦    |
| 셀렉터 추측          | 화면 안 보고 시작 → 틀리면 왕복          |
| 타이밍 함정          | 화면 다 그려지기 전 클릭하면 실패(flaky) |
| 한 번 쓰고 버릴 코드 | 즉석 확인엔 과함                         |

browser-verifier는 네가 보던 그 화면에 바로 붙으니까 **그 상태 그대로 확인.** 훨씬 편해요.

---

## 6. "그럼 Playwright MCP는 언제 좋아?"

**네 웹사이트 말고, 딴 데서 뭔가 할 때** 좋아요.

```
- 네이버 들어가서 검색하기
- 다른 사이트에서 자료 긁어오기 (스크래핑)
- 파일 올리고 내려받기
- 회원가입부터 결제까지 긴~ 과정 쭉 해보기 (탐색적 E2E)
- 멀티 탭 교차 작업
- 구글/깃허브 OAuth 로그인 자동 통과
```

browser-verifier는 **"네 화면 확인"만** 잘해요. 이런 딴 일은 Playwright MCP가 잘해요.

| 영역                    | browser-verifier | Playwright MCP |
| ----------------------- | :--------------: | :------------: |
| 내 localhost React 검증 |     ✅ 강함      |       △        |
| 임의 사이트 조작        |        ❌        |       ✅       |
| 탐색적 E2E              |        △         |       ✅       |
| 스크래핑/데이터 수집    |        ❌        |       ✅       |
| 멀티 탭 교차 작업       |        ❌        |       ✅       |
| 파일 업/다운로드        |        ❌        |       ✅       |
| 외부 OAuth 로그인       |        ❌        |       ✅       |

---

## 7. "테스트 코드"는 또 뭐야?

🍜 비유: **라면 먹기 vs 정식 요리**

|                          | 비유      | 설명                                                                  |
| ------------------------ | --------- | --------------------------------------------------------------------- |
| **즉석 검증** (browser-verifier) | 라면      | "지금 이거 됐나?" 빠르게 한 번. 가볍게.                               |
| **테스트 코드**          | 정식 요리 | 단계를 코드로 다 적어두고, 몇 번이고 똑같이 돌림. 두고두고 쓰는 자산. |

**즉석 확인에 테스트 코드를 쓰면 단점:**

- 빈 브라우저라 상태를 매번 다시 만듦
- 셀렉터를 추측해서 써야 함 (틀리면 왕복)
- 타이밍 대기 코드를 직접 넣어야 함
- 한 번 보고 버릴 건데 정식 파일 만들기 = 과식

> 잠깐 확인 = 라면(browser-verifier), 영구 회귀 방어 = 정식(테스트 코드).

---

## 8. 제일 똑똑한 방법 (두 도구 합치기)

```
1. browser-verifier로 "어떻게 하면 되는지" 먼저 검증
2. 그 검증된 길을 → 테스트 코드(.spec.ts)로 만들기
```

👉 길을 **이미 가봤으니까**, 코드 짤 때 **셀렉터 추측(환각)이 줄어요.**
👉 라면(빠름) + 정식(튼튼함) 둘의 장점을 합치는 거예요.

단, 번역 갭은 있어요 (click 방식·노이즈 필터·대기는 런타임이 숨기던 부분이라 다듬기 필요).

## 9. "AI 판단" vs "코드 판정" (핵심 차이)

검증할 때 **합격/불합격을 누가 정하느냐**가 두 도구의 진짜 차이예요.

### browser-verifier = 코드가 판정 (OMR 자동 채점기)

```
1. AI:  "버튼 글자 '저장' 맞나 봐줘"   (규칙만)
2. 코드: 글자 꺼냄 → "저장"==기대값 비교 → ✅/❌   ← 코드가 판정!
3. AI:  결과만 받음
```

### Playwright MCP = AI가 판정 (사람이 답안 읽고 채점)

```
1. AI:  "화면 떠줘"  (snapshot)
2. 코드: 화면을 글로 길게 떠다 줌  ← 여기까지만, 판정 안 함
3. AI:  그 글 읽고 → "음 저장 맞네, 합격인 듯"   ← AI가 판정!
```

|                      | browser-verifier | Playwright MCP     |
| -------------------- | ---------------- | ------------------ |
| 도구 코드            | 미리 짜둠        | 미리 짜둠          |
| 화면 만지기(클릭 등) | 코드             | 코드               |
| **합격/불합격 판단** | **코드가** ✅    | **AI가** 🧠        |
| 속도·정확도          | 빠르고 일정      | 느리고 가끔 흔들림 |
| 비용(토큰)           | 거의 안 씀       | 많이 씀            |

> 중요: Playwright MCP도 **코드는 미리 짜여 있어요.** AI가 코드를 즉석으로 짜는 게 아니에요.
> AI가 즉석으로 하는 건 **"판단"**이지 코드가 아니에요.

비유 — 계산기 vs 암산: 검증은 "정확히 맞나"가 중요하니까 **계산기(코드 판정)**가 더 어울려요.

## 10. 안에서 어떻게 돌아가나 (browser-verifier 내부)

### 자연어 → 실행, 4단계

```
1. 너:        "버튼 글자 봐줘"                          (사람 말)
2. Claude:    { 종류:"버튼글자", 위치:"save-button", 기대값:"저장" }   (규칙으로 통역)
3. 플러그인:   page.locator("save-button").textContent()  (Playwright 실행)
4. 브라우저:   진짜 찾아서 글자 돌려줌 → 비교 → ✅
```

- **1번만 내가(AI) 하는 일**: 사람 말 → 정확한 규칙으로 통역.
- 2~4번은 전부 코드와 브라우저.

### 2 → 3은 어떻게 넘어가나? — "이름표로 짝꿍 코드 찾기"

규칙 안에 **이름표(`종류`)**가 있어요. 플러그인은 그 이름표로 **미리 정해둔 짝꿍 코드**를 찾아 실행해요.

```js
// 플러그인이 미리 만들어둔 "이름표 → 코드" 표
검사방법 = {
  "버튼글자": (규칙) => 브라우저.찾기(규칙.위치).글자 == 규칙.기대값,
  "현재주소": (규칙) => 브라우저.주소() == 규칙.기대값,
  "콘솔에러": (규칙) => 브라우저.에러개수() == 0,
}

함수 실행(규칙):
  이름표  = 규칙.종류             // "버튼글자"
  짝꿍코드 = 검사방법[이름표]      // ★ 표에서 찾기 = 2→3 넘어가는 순간
  return 짝꿍코드(규칙)           // 실행
```

> 비유: **자판기.** 버튼(이름표) 누르면 정해진 음료(코드)가 나와요. 안에서 어떻게 나오는지 몰라도 됨.

### Playwright 코드는 미리 짜여 있다

```
[플러그인 안 — 미리 짜여 있음]
"버튼글자" → page.locator(...).textContent()   ← 이미 작성됨
"현재주소" → page.url()                         ← 이미 작성됨
"콘솔에러" → page.errors()                      ← 이미 작성됨
```

→ 플러그인 만든 사람이 **한 번 다 짜놨어요.** AI는 이름표로 **불러 쓰기만** 함.
→ 예외: "테스트 코드 짜줘" 할 때만 AI가 Playwright를 **직접 새로** 써줘요.

### Playwright 코드 vs 나머지 JS 코드의 역할

```
Playwright 코드 = 손과 발  (브라우저를 실제로 만짐)
나머지 JS 코드  = 머리·입  (판단·통역·정리)
```

| 주방 역할                           | 플러그인에서   | 실제 파일            |
| ----------------------------------- | -------------- | -------------------- |
| 🖐️ 불 쓰는 요리 (브라우저 만지기)   | **Playwright** | `cdp/`, `actions.ts` |
| 📋 주문 받기 (규칙 받기)            | 도구 정의      | `tools/`             |
| 🔀 주문 → 레시피 연결               | 라우팅         | `server.ts`          |
| ⚖️ 기대값 vs 실제 비교 (합격 판정)  | 검증 로직      | `runtime/verify/`    |
| 🧹 노이즈 청소 (쓸데없는 에러 거름) | 필터           | `checks.ts`          |
| ⏳ 화면 다 그려질 때까지 대기       | 안정화         | `waitPageStable.ts`  |
| 📦 결과 예쁘게 포장 (PASS/FAIL)     | 결과 포맷      | `lib/result.ts`      |
| 🔁 여러 단계 task 순서대로 실행     | task 러너      | `runtime/tasks/`     |

"버튼 글자 봐줘" 한 번에 일어나는 일 중 **Playwright는 4번 한 군데뿐**, 나머지는 다 그냥 JS예요:

```
1. tools/verify.ts        규칙 받음              [주문]
2. server.ts              담당 연결              [라우팅]
3. waitPageStable.ts      화면 준비될 때까지 대기  [안정화]  ← Playwright 아님
4. actions.ts (Playwright) 진짜 버튼 찾고 글자 꺼냄 [요리]    ← Playwright
5. runtime/verify/        "저장"==기대값 비교     [판정]    ← Playwright 아님
6. lib/result.ts          "✅ PASS"로 포장        [포장]    ← Playwright 아님
```

## 11. 그래서 이 MCP의 독보성은 뭔가?

```
핵심 아이디어 = 코드가 판단한다  ✅
진짜 독보성   = "코드 판단"을 + "자연어 MCP"로 + "네 라이브 화면"에서  (조합)
```

"코드로 판단"은 **심장**이고, 독보성은 그걸 **어떻게 포장했냐**에 있어요.

### "코드 판단"만으론 부족한 이유

사실 **코드로 판정하는 도구는 이미 많아요.**

```
Playwright test, Cypress, Jest...  ← 다 코드가 합격/불합격 판정
```

"코드가 판단한다" 자체는 새로운 게 아니에요. 테스트 프레임워크는 원래 다 그래요.
→ 이 MCP가 다른 건 **"코드 판단"을 어디에 끼워넣었냐**예요.

### 진짜 독보적인 3개 조합

| 보통 테스트 도구                  | 이 MCP                                                |
| --------------------------------- | ----------------------------------------------------- |
| 코드를 **사람이 미리 다 짜야** 함 | **자연어로** 시키면 코드 판정이 돎                    |
| **새 브라우저**에서 격리 실행     | **네가 보던 라이브 화면**에 붙음                      |
| 범용 (HOW 다 직접)                | **React 맞춤** (hydration·retry·노이즈 런타임이 숨김) |

비유:

> "칼로 자른다"(코드 판정)는 누구나 함.
> 근데 **"말로 시키면 + 네 주방에서 + 재료별 손질까지 알아서"** = 이 조합이 특별.

### 한 문장 정의

> "AI가 화면을 눈으로 읽고 판단하던 걸 → **결정적(deterministic) 코드 판정**으로 바꾸되,
> 그걸 **자연어 MCP**로 부르고 **개발자의 라이브 React 화면**에 붙여서, **즉석 검증 루프**에 끼워넣은 것."

여기서 **"코드 판정"이 심장**, 나머지(자연어·라이브·React)가 **그걸 살아있게 만드는 몸**이에요.

## 12. "매번 다른 UI를 어떻게 다 검증해?" — 고정 틀 + AI가 채우는 빈칸

검사 항목이 코드에 박혀 있는데, 어떻게 매번 다른 화면을 검증할까? → **두 개의 층**으로 나뉘기 때문이에요.

```
고정된 것   = "어떻게 검사하나"(방법) + "검사 종류"(블록 모양)
매번 다른 것 = "무엇을 검사하나"(셀렉터·기대값)  ← AI가 채움
```

고정된 건 **방법과 틀**이지, **내용**이 아니에요.

### 비유: 빈칸 채우기 시험지

```
틀(고정):   "____ 의 글자가 ____ 이어야 한다"
              ↑셀렉터    ↑기대값
AI가 채움:  "저장버튼의 글자가 '저장' 이어야 한다"
            "제목의 글자가 '회원가입' 이어야 한다"
```

틀은 하나인데 빈칸을 다르게 채우니 **무한히 다른 UI**를 검증할 수 있어요.

### 비유: 레고 블록

검증 "종류"는 레고 블록 모양처럼 정해져 있어요 (11종): `computed_style`, `class_present`, `route`, `modal_open`, `heading_present`, `input_count`, `no_errors` ...

같은 블록으로 매번 다른 걸 조립해요:

```
오늘:  [route=/home] + [no_errors]
내일:  [computed_style: padding=16px] + [class_present: bg-blue]
모레:  [modal_open] + [heading=신규가입] + [input_count≥3]
```

→ **종류는 고정, 조합과 값은 AI가 매번** → 어떤 UI든 커버.

### 두 도구(semantic_state vs verify)의 역할

| 도구             | 성격                                                 | 예                   |
| ---------------- | ---------------------------------------------------- | -------------------- |
| `semantic_state` | 아무 페이지나 통하는 **공통 정보** (고정 체크리스트) | 주소·모달·에러·로딩  |
| `verify`         | **이 UI 전용** 검증 (AI가 빈칸 채움)                 | 이 카드 padding 16px |

집마다 주소·현관문은 공통(→ semantic_state), 인테리어는 제각각(→ verify).

### AI는 빈칸(셀렉터·기대값)을 어디서 찾나? — 3곳

| 출처                           | 뭘 얻나        | 예                                          |
| ------------------------------ | -------------- | ------------------------------------------- |
| **① 네 코드 파일** (제일 흔함) | 셀렉터, 기대값 | JSX의 `data-testid`, `className`, 버튼 글자 |
| **② 네 지시·Figma**            | 기대값         | "padding 16px여야 해"                       |
| **③ 라이브 화면** (먼저 떠봄)  | 실제 셀렉터·값 | `semantic_state`로 확인 후 채움             |

보통 흐름:

```
1. AI가 네 컴포넌트 코드 읽음        → selector 알아냄   (①)
2. 코드의 className / Figma 스펙     → expected 알아냄   (①②)
3. verify 빈칸 채워서 호출
4. 코드가 실제 화면과 비교 → ✅/❌
```

> 비유: AI가 **설계도(코드)** 보고 "여기 문은 파란색이어야 하네" 알아낸 뒤,
> **실제 건물(화면)** 가서 "진짜 파란색 맞나"를 코드로 검사시키는 것.

### 정리 — 무엇을 누가 정하나

| 무엇을 정하나                                  | 누가                                    |
| ---------------------------------------------- | --------------------------------------- |
| 검사하는 방법 (querySelector·getComputedStyle) | **코드 (고정)**                         |
| 검사 종류 11개 (블록 모양)                     | **코드 (고정)**                         |
| 어떤 종류 블록 쓸지                            | **AI**                                  |
| 셀렉터(어디를) / 기대값(뭐여야)                | **AI** (코드·지시·라이브에서 찾아 채움) |
| 실제 조회·비교·판정                            | **코드**                                |

## 13. Playwright MCP는 이 부분이 어떻게 달라?

같은 "빈칸 채우기"를 두 도구가 다르게 해요.

|               | browser-verifier                                | Playwright MCP                               |
| ------------- | ----------------------------------------------- | -------------------------------------------- |
| 검사 종류(틀) | **검증 전용 11종** (no_errors, computed_style…) | 검증용 틀 없음. 액션 도구(click·snapshot)만  |
| 셀렉터 채우기 | 코드 파일 / Figma / `semantic_state`에서        | 주로 **snapshot(접근성 트리) 읽고** 거기서   |
| 기대값        | AI가 채우고 → **코드가 비교**                   | 기대값 개념 약함 → **AI가 눈으로 맞나 판단** |
| 합격/불합격   | **코드가** 판정 ✅                              | **AI가** 판정 🧠                             |
| 화면 읽는 양  | 필요한 값만 **콕** (토큰 적음)                  | 트리 **통째로** AI에 (토큰 많음)             |

### 같은 일을 시키면

```
[browser-verifier]
AI: 코드에서 selector·expected 찾음
  → verify({ type:"computed_style", selector:"[data-slot=card]", prop:"padding", expected:"16px" })
  → 코드가 "16px"==실제 비교 → ✅   (판정=코드)

[Playwright MCP]
AI: browser_snapshot()  → 접근성 트리 글로 받음
  → AI가 그 글 읽고 "음 카드가 있네... padding은 트리에 안 나오는데?"
  → 판단 흔들리거나 추가 조회 필요   (판정=AI, CSS 값은 트리에 잘 안 보임)
```

> 핵심 차이: browser-verifier는 **빈칸을 코드/스펙에서 채우고 코드가 판정**,
> Playwright MCP는 **빈칸을 snapshot에서 채우고 AI가 판정**.
> 그래서 CSS·토큰 같은 "정확한 값" 검증은 browser-verifier가 강하고, 자유로운 탐색은 Playwright MCP가 강해요.

## 14. browser-verifier는 화면 "조작"이 약한가?

약해요. **하지만 "못해서"가 아니라 "안 하려고 만들어서"예요.**

```
조작 능력 자체 = 있음 (click, fill, navigate 등 도구 있음)
약한 이유      = "검증"이 목적이라 조작은 딱 검증에 필요한 만큼만 넣음
```

### 이유 1: 목적이 "검증"이지 "조작"이 아님

조작은 "확인하려고 잠깐 거치는 단계"일 뿐이에요. (버튼 눌러 모달 띄워야 모달을 검증하니까)
그래서 조작 도구는 검증에 필요한 최소한만: `click`, `fill`, `press_key`, `select_option`, `navigate`.

### 이유 2: 빠진 조작 기능들

| 못 하는 조작           | browser-verifier | Playwright MCP |
| ---------------------- | :--------------: | :------------: |
| 드래그 앤 드롭         |        ❌        |       ✅       |
| 마우스 hover           |        ❌        |       ✅       |
| 파일 업로드/다운로드   |        ❌        |       ✅       |
| 스크롤 제어            |        ❌        |       ✅       |
| 탭 생성·전환           |  ❌ (목록만 봄)  |       ✅       |
| 네이티브 alert/confirm |        ❌        |       ✅       |

→ "검증 루프"에 거의 안 나와서 뺀 거예요.

### 이유 3: "탐색하며 조작"을 안 함

Playwright MCP는 화면 보며 즉흥적으로 다음 행동을 정해요(탐색적 조작).
browser-verifier는 **미리 정한 단계(task의 11 ops)만** 실행: `goto · click · fill · navigate · reload · wait_* · verify · screenshot`.

> 비유: **시험 감독관 vs 만능 비서.**
> 감독관(browser-verifier)은 채점이 일 — 시험지 나눠주는 정도(조작)만. 커피 타오라(드래그·업로드)는 안 함.
> 비서(Playwright MCP)는 뭐든 시키면 함(조작 다 됨) — 대신 채점은 직접 눈으로.

## 15. 조작을 전부 안 넣은 이유 — 토큰? 성능?

```
토큰        → ⭕ 관련 있음 (도구 많으면 항상 토큰 더 먹음)
실행 속도   → ❌ 거의 무관 (안 쓰는 도구는 속도에 영향 없음)
진짜 큰 이유 → AI가 "맞는 도구 고르기" 쉽게 (집중)
```

### 1. 토큰 — 맞아요

도구 하나하나의 **설명서(스키마)가 항상 대화 맥락에 깔려 있어요.** 도구가 많으면 하나도 안 써도 그 목록만으로 토큰을 먹어요.

> 비유: 메뉴 500개짜리 메뉴판은 주문 안 해도 넘기는 데만 시간·종이 낭비.

### 2. 실행 속도 — 거의 무관

드래그 도구를 추가한다고 클릭이 느려지진 않아요. 안 쓰는 도구는 가만히 있어요. → 성능 때문에 뺀 게 아님.

### 3. 진짜 큰 이유 — "맞는 도구 고르기"

도구가 많을수록 AI가 헷갈려서 엉뚱한 걸 골라요.

```
도구 5개  → "검증이면 verify네" 딱 고름  (정확)
도구 50개 → "verify? inspect? snapshot? eval? drag?..." 헷갈림  (실수↑)
```

README에 **"Phase 6 — Surface narrowing(도구 줄이기)"**으로 명시. 일부러 14개로 좁혔어요.

> 비유: 리모컨 버튼 3개면 안 헷갈림. 50개면 "어디 누르지?" 헤맴.

### 우선순위 정리

| 이유                       | 영향                     |    크기    |
| -------------------------- | ------------------------ | :--------: |
| AI 도구 선택 정확도 (집중) | 엉뚱한 도구 안 고름      | 🥇 제일 큼 |
| 토큰 절약                  | 도구 목록이 맥락 덜 차지 |  🥈 있음   |
| 결정성·유지보수            | 예측 가능, 관리 쉬움     | 🥉 부수적  |
| 실행 속도                  | —                        | 거의 무관  |

> 토큰 절약도 맞지만, 제일 큰 이유는 **"AI가 맞는 도구를 헷갈림 없이 고르게"** 하려는 것. 속도 때문은 아니에요.

## 16. 그래서 browser-verifier를 한 문장으로 정의하면

> **"개발 중 검증"이라는 한 가지 일에만 집중해서, 흔들리면 안 되는 판정은 코드에 맡기고(AI 추론 제거), AI에겐 규칙 작성만 남겨, 불필요한 조작·도구를 쳐낸 빠르고 결정적인 검증 도구.**

핵심 키워드 4개:

| 키워드 | 의미 |
|--------|------|
| **좁힘** | 검증 한 가지에 집중, 잡기능 제거 |
| **결정적** | 판정을 코드가 → 항상 같은 결과 |
| **라이브** | 네가 보던 화면에 붙음 (개발 시점 특화) |
| **저비용** | 토큰·왕복 적음, 빠름 |

### 미세 보정 — AI 추론은 "제거"가 아니라 "이동"

AI 추론이 완전히 사라진 건 아니에요. **위치가 바뀐** 거예요.

```
[Playwright MCP]   AI가 → 판정까지 추론        (결과가 흔들림)
[browser-verifier] AI는 → "규칙 만들기"까지만 → 판정은 코드  (결과 일정)
```

- ❌ AI 추론 0
- ⭕ AI 추론을 **"검증 판정"에서 빼고, "규칙 작성"에만 남김**

> 비유: 시험에서 **채점은 기계(코드)**, 사람(AI)은 **문제 출제**만.
> 사람 추론이 없어진 게 아니라, 흔들리면 안 되는 "채점"에서만 뺀 거예요.

---

## 전부 한 줄로

> **browser-verifier = 자동 채점기(OMR)** → 정답 정해두고 코드가 정해진 칸만 읽어 기계적으로 ✅/❌. 네가 보던 화면에서 빠르게. 개발 중 검증에 딱.
> **Playwright MCP = 눈으로 채점하는 조교** → 화면(트리) 통째로 읽고 AI가 판단. 새 브라우저로 딴 데서 뭐든 시키기. 자동화에 딱.
>
> 둘은 싸우는 게 아니라 **쓰는 데가 달라요.** 검증(코드 판정)이냐 vs 조작(AI 판단)이냐. 😊
